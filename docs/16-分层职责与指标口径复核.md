# 分层职责与指标口径复核

更新：2026-11-18。对应整改清单第6、7项。依据《大数据之路》所代表的分层、公共数据与复用思想，并以阿里云官方DataWorks文档交叉核对。没有取得完整教材，下面区分官方文档可验证的方法与本项目的具体取舍。[A1][A2]

## 1. 逻辑分层与物理实现

| 逻辑层 | 职责 | 本项目实际对象 | 复用或边界 |
| --- | --- | --- | --- |
| ODS | 来源原样保存、原始位置与对象追溯 | ods.source_record及data/ods/files；OPS来源对象登记 | 保留逐条payload与源对象，避免把质量清洗后的记录冒充原始 |
| DIM | 一致性维度、角色复用、未知成员、历史解释 | 现有dwd.dim_date/time/zone/station/transport/bike_type/weather_daily | 同一维度跨两行程过程复用；不是第8张新表 |
| DWD | 业务过程最细粒度事实、质量资格 | dwd.fact_taxi_trip、dwd.fact_bike_trip | 一行一有效源行程/ride_id，保留维度键和追溯键 |
| DWS | 统一、可复用的公共汇总与组成项 | trip_day、trip_hour、zone_hour、od_day、weather_group | 日期/小时/空间/天气粒度供多个问题复用，计算一次、统一分母 |
| ADS | 面向看板的命名、派生结果与服务发布 | 七结果表、ClickHouse副本、ads.bi_*视图 | 均值/比率、名称补全、发布隔离；不是所有表都必须改变粒度 |
| OPS（旁路管理） | 采集、质量、构建、版本与发布审计 | ingest_batch、source_object、quality_result、quarantine_record、publication | 管理元数据不混作独立出行业务主题；release_pointer为服务控制 |

阿里官方文档单列DIM、DWD、DWS并可归入公共模型层CDM，ODS负责引入、ADS负责应用。[A1][A2] 本项目逻辑上明确五类职责，现有物理业务schema仍为ODS、DWD、DWS、ADS，OPS旁路管理；因此可表述“原四层物理实现，公共层内区分DIM与DWD职责”，不能写成已经完成新增物理`dim`数据库或表迁移。

## 2. ADR-001：保留物理dwd.dim_*，独立明确DIM职责

**问题**：是否为模仿层数把七个维度迁到独立schema？

**决定**：本轮保留物理`dwd.dim_*`与Delta路径，通过总线矩阵、独立维度职责、输入版本固定及公共使用约束落实DIM。原因是既有源码、模型契约、已发布构建清单及质量证据都引用这些稳定身份；仅改前缀没有增加业务价值，会改变代码指纹并要求重跑。当前数据规模和两个业务过程无需因名称拆库。

**后果**：报告和图必须同时标注逻辑职责与实际表名；不能宣称实现了独立物理DIM层。未来若治理权限、多个业务域或部署边界需要独立schema，应做版本化迁移并验证全部外键、快照和复跑，不在本轮无依据重写历史数据。

## 3. ADR-002：允许DWS与部分ADS同粒度，明确各自职责

- `trip_day/hour`：DWS保存`trip_count`、时长/距离的分子与有效分母、空间匹配计数和完整性；ADS补交通名称、平均值、映射率及发布版本。一个DWS同时服务日趋势、均值、覆盖率和周类型比较。
- `zone_hour`：DWS提供区域小时出发量及完整性骨架；ADS补名称/行政区和发布隔离。地图、区域排行、行政区比较、选区小时曲线复用同一公共数值。到达/净流入不完整时保持NULL，不因有列就宣称业务完成。
- `od_day`：公共OD计数由DWS统一定义，ADS补两端名称与发布；Top20、集中度和矩阵可从同一全量OD结果派生。不能用导出的Top20作为全量分母。
- `weather_group`：DWS保存`trip_count/complete_days`，ADS生成日均、同方式同周类型基准及比率，服务天气比较和样本说明。
- 质量ADS来自OPS，属于质量应用结果，允许独立支路，不强行先造一张同名DWS。

同粒度不是无意义重复的充分证据。数值、解释属性、面向应用的派生和候选版本隔离有明确目的；也不为了画层而把同一公式在每层重复计算。当前不增加DWT，仅在新的稳定主题复用需求出现时再评估。

## 4. 指标与口径复核表

| 指标 | 分子/组成项 | 分母/聚合范围 | 复核结论 |
| --- | --- | --- | --- |
| 有效行程量 | COUNT有效粒度事实；DWS trip_count | 当前月/方式，可按日小时相加 | 现有实现保持；包含空间未知但核心有效行程 |
| 平均时长（分钟） | SUM(duration_sum_seconds) | SUM(duration_count)×60 | 跨组重算；零分母NULL |
| 出租车平均距离（公里） | SUM(distance_sum_km) | SUM(distance_count) | 距离资格单独判断；骑行NULL |
| 当地小时日均量 | 该当地小时内总行程量 | 选中范围来源完整的日期数 | 完整六月为30；含完整零日；不得只数有行程日 |
| 周类型日均量 | 同方式同周类型总行程量 | 该周类型完整日期数 | 周一至周五与周末分别分母，不称已识别法定假日 |
| 方式内小时占比 | 同方式某小时行程量 | 同方式同日期范围总量 | 各方式合计100%；不是全市交通分担率 |
| 区域出发量 | 起点成功匹配区域的出发记录 | 按区域/方式/时间汇总 | 对齐origin_mapped_count；不要求终点匹配 |
| OD行程量 | 两端匹配的开始队列行程 | 按日期/方式/起终区汇总 | 保留方向与同区OD，对齐od_mapped_count |
| OD Top20集中度 | 相同范围Top20全部行程量 | 同范围完整OD总量 | 只作总量比例；Top20数值取全量而非样例 |
| 三种空间覆盖率 | 各origin/destination/od_mapped_count之和 | 同范围trip_count之和 | 不受单区域/行政区筛选误改分母 |
| 降水组日均量 | 同月/方式/周类型/降水组trip_count | 对应complete_days | 不可将微量降水或缺失并入基准 |
| 天气需求比率 | 目标组日均量 | 本方式本周类型no_measurable基准日均 | 无基准、零分母NULL；不跨组平均比率 |
| 天气独立天数 | 按方式内各天气/周类型完整日计数 | 同一自然日不跨方式加倍 | 每种方式合计30天，不把60叫60个天气日 |
| 数据有效率 | accepted_rows | 对应解析成功input_rows | 隔离/重复/范围外互斥；解析失败另报 |
| 完整到达/净流入 | 当前无完整边界输入 | 需五月开始且六月结束等边界来源 | 保持不可用，不作0，不从六月OD冒充 |

## 5. 天气与空间分析的粒度陷阱

1. `dim_weather_daily`是日级上下文；温度/降水等数值不能沿行程求和。对比按日先汇总出行量后分天气组，避免每天记录量不同给天气均值错误加权。
2. 已发布`weather_group`是整月分组结果，当前不支持任意日期窗口重算；若要筛某几天必须回到日明细与对应天气按日期重聚合。
3. 区域出发总量与总体有效行程量是不同子集；选区时段曲线的全局参照应使用相同空间匹配资格。
4. 已有小时骨架只验证六月，无夏令时切换；扩月应处理重复/不存在小时，不把当前30×24写成通用规则。

## 复现本次结构核查

在项目根目录运行（无需Docker、数据库或网络）：

```powershell
python tools/verify_model_design.py --output-dir outputs/2026-11-18-theme-definition-e721eb90/model
```

`--output-dir`可显式指定其他已包含模型图与参考回执的目录；相对路径始终相对于项目根解析。检查会重新生成`model-design-review.json`并在失败时返回非零状态。

如需重新生成图，可运行`python tools/build_model_review.py --output-dir outputs/2026-11-18-theme-definition-e721eb90/model`，依赖Pillow；非Windows环境须通过`--font`、`--bold-font`提供中文字体路径。参考网页回执只记录历史访问事实，核查命令不会伪造新的联网验证。
