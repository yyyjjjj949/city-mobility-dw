# Kimball案例借鉴与事实表设计

更新：2026-11-18。对应整改清单第2、7项；以实际契约、DWD与DWS代码为依据。物理表、作业与质量规则本次保持原版本。

## 1. 借鉴方法与适配边界

采用Kimball四步法：选择业务过程、声明粒度、识别维度、识别事实，先决定每一行代表的业务事件，再决定字段。粒度是一行事实的业务定义，不是主键字段列表。[K1][K2]

课程推荐的《数据仓库工具箱》可按运输类案例理解行程事件、出发/到达地点与时间的角色。本项目没有取得课程群完整教材及第4章课件，不声称已通读课程指定版本，也不照搬航空业的旅客、票券、航段、收入或累积快照。当前可核验的方法来源是Kimball官方技术资料；正式报告的教材版本、页码由实际使用版本补充，不能臆造。

| 运输类建模启发 | 本项目适配 | 不采用的推断 |
| --- | --- | --- |
| 围绕一次运输活动声明粒度 | 出租车源行程记录、单车ride_id骑行分别建事实 | 不把一个小时或一个区域当作明细行程 |
| 区分地点和时间角色 | 起点/终点、开始/结束引用同一套区域/日期/分钟维度 | 不为每个角色复制不同口径的维度 |
| 不同业务过程可共享分析维度 | 两个行程过程共享日历、分钟、区域、方式、天气上下文 | 不直接连接两个事实表形成多对多 |
| 先保存可汇总的组成项 | 时长、距离之和与对应有效分母保存至公共汇总 | 不平均每日平均值，不编造单车距离 |

## 2. 出租车行程：四步设计

1. **选择业务过程**：纽约Yellow Taxi一次历史行程的完成记录。主题问题是日期/小时活动、区域与OD、天气背景比较，不是订单支付全生命周期。
2. **声明粒度**：`dwd.fact_taxi_trip`的一行是一个通过核心时间/时长校验、处于目标开始日期范围的原始出租车记录。来源无可验证的全局业务行程ID，`trip_key=source_record_key`，该键指向ODS来源位置；它保证来源行身份，不证明两个内容相同的源行是同一业务事件。不得仅按内容摘要删除这类记录。
3. **确定维度**：开始/结束日期、开始/结束当地分钟、起点/终点区域、交通方式、开始日期对应中央公园日天气。角色键见第15号文档。未知区域0保留该行程，区域子集另行选择；缺失上下文不伪造成真实成员。
4. **确定事实与度量**：每行隐含计数1；`duration_seconds`与`duration_metric_eligible`；`distance_km`与`distance_metric_eligible`。源乘客数、金额分项等可追溯保留，但没有据此宣称已实现客流人数或收入主题。核心行程有效不等于所有距离/费用字段都适合分析。

身份与粒度说明：同一源记录的重复导入由ODS幂等身份控制；源文件若修订则按来源对象和受影响分区重建。`content_fingerprint`用于检查候选相似记录，不能替代真实业务ID。`vendor_id`、`payment_type`等保留源编码，当前不将其宣称为已建设的独立一致性维度。

## 3. 共享单车骑行：四步设计

1. **选择业务过程**：Citi Bike一次历史骑行的完成记录。它与出租车是两个业务过程，共享城市历史出行总主题。
2. **声明粒度**：`dwd.fact_bike_trip`的一行是一个有效、规范化且无业务内容冲突的`ride_id`。相同ID且相同业务内容保留一个；同ID出现不同内容阻断发布，不能任选一行。
3. **确定维度**：共享五类维度，并增加起站/终站与车型。站点采用`namespace×reference_period×station_business_key`的期间快照键；终点同样使用该来源开始月份的站点快照，不从当前站点名称或容量倒填历史。
4. **确定事实与度量**：隐含行程计数1、有效骑行时长。源无实际路线距离，不用起终点直线距离冒充骑行距离。`member_type`作为当前事实中的低基数描述属性保留，不将本项目称为已完成会员行为画像。

`ride_id`是无独立描述维表的事件标识，可按退化维度理解；出租车的`trip_key`则主要是来源行追溯标识，不能等同源系统提供的业务单号。行程标识本身不是可加度量。

## 4. 事实表类型、粒度和度量汇总

两张表均为已完成行程事件的事务粒度事实；不为每次下载生成一条“行程事实”，不使用实时库存快照，也未实现订单状态累积快照。历史站点“快照”是维度的期间管理，不是周期快照事实。

| 类别 | 字段/表达式 | 可汇总条件 | 限制 |
| --- | --- | --- | --- |
| 行程次数 | 每条符合目标粒度的事实计数1 | 按不重叠日期、区域、方式等维度分组可加 | 出租车计数是有效源记录数；两方式合计不是全市总量 |
| 有效时长组成项 | duration_seconds与有效记录数 | 在同一资格规则、同一事件粒度下可加 | 未纳入时长指标的记录不进入分子和分母 |
| 出租车距离组成项 | distance_km与有效距离记录数 | 只对距离合格出租车记录求和 | 骑行保持NULL，不能混作0公里 |
| 平均值 | SUM(分子)/SUM(分母) | 非可加派生度量，跨组需重算 | 不能SUM或AVG各日平均值 |
| 占比/覆盖率 | 匹配/选定子集数量÷相同范围分母 | 非可加比率，分子分母分别聚合 | 分母范围、样本子集与发布版本必须一致 |
| 天气组样本天数 | complete_days | 固定方式内对不重叠天气/周类型分组可加 | 跨方式同一天重复，不可加成独立天气样本 |
| 天气需求比率 | 目标组日均÷本方式本周类型基准日均 | 非可加，基准一致才有可解释比较 | 不能跨方式或周类型直接平均 |
| 站点容量/日温度等 | 维度上下文中的数值属性 | 不能沿行程行求和 | 按天气/站点本身粒度分析需另立规则或事实 |

当前范围没有库存余额等半可加业务事实。不能为了展示三种术语而把任意字段标成半可加；若以后接入库存快照，应声明站点×观察时刻粒度并禁止跨时刻求和。[K4]

## 5. 天气上下文的特殊处理

`dim_weather_daily`粒度为气象站×源观察日期，含降水分组及温度、降水、风等测量属性。当前把它作为两类行程开始日的观察性上下文，用其分组或筛选，再聚合行程量。它含有数值观测，不是可以随行程累加的事实度量；把同一天温度重复连接到数十万行程后求和没有业务意义。

当前仅一个站，时间关联必须一日唯一；代码检查日期完整性与可用性。若以后开展多站/多时次气象监测，应独立建立天气观测事实及站点/时间维度，再按明确地理时间规则与行程分析，不直接事实对事实连接。此设计说明避免将本模型宣称为完全纯粹、所有属性均为描述文本的星型。

## 6. 质量和追溯约束

- 事实逻辑键唯一、核心非空及维度引用由质量任务校验；Delta/ClickHouse排序键不提供关系数据库式强制外键。
- 未知成员占位与“不参与区域指标”是两件事：记录可保留，空间资格标志决定子集。
- 日期分区采用纽约开始日期；跨月行程仍归开始队列。没有五月边界数据时，不发布完整六月事件到达量与净流入。
- 事实保存`source_record_key`、`batch_id`、`rule_version`；构建清单固定输入Delta与维度版本，支持按来源回查。
